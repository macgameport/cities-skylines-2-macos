## 2. Target

Apple's file-system guidance gives each kind of file a place under `~/Library` and tells apps to keep the files they create themselves there, by convention in a subfolder named for the app's bundle identifier. This project is several apps, so it uses its own name, as Porting Kit does on this Mac.

| Kind | Place | Used for |
|---|---|---|
| The apps | `~/Applications` | wrappers and double-click apps (unchanged) |
| Files an app keeps for itself | `~/Library/Application Support/<name>/` | **the runtime folder**: what a game runs, and a game's own state |
| Logs | `~/Library/Logs/` | the two launcher logs (unchanged) |
| Things an app can make again | `~/Library/Caches/<name>/` | nothing of ours: section 1 shows the workspace is not that |
| "Data used by Xcode and other developer tools" (Apple's table, the `Developer` row) | `~/Library/Developer/` | **the workspace** (O3) |

```
~/Library/Application Support/1launcher/      the data root
├── cities-skylines-2/                         the runtime folder: the 22 deployed files and revenv/
└── surviving-mars-relaunched/                 backup/ and runs/ (unification O9)
~/Library/Developer/1launcher/                 the work root: durable, and no space in its path
├── cities-skylines-2/                         the workspace: everything else in today's ~/cs2-patch, names unchanged
└── surviving-mars-relaunched/                 engine/ (O4)
```

**Two rules map every old path.** The seven runtime names (`launch-cs2-dxmt11.sh`, `launch-cs2.sh`, `repatch.sh`, `cs2-display-profile.sh`, `patch-modconflict-badge.py`, `patches/`, `revenv/`), and any launcher backup beside them (`launch-cs2*.sh.bak`), become `<data root>/cities-skylines-2/<name>`. Every other `~/cs2-patch/X` becomes `<work root>/cities-skylines-2/X`. Nothing is renamed or regrouped, and the four trees stay beside each other. On the Studio the home folder ends with neither `~/cs2-patch` nor, after Phase 3, `~/sm-patch`.

Why two places. The runtime folder is what the standard's Application Support is for, and P1 shows an app can run scripts there. The workspace is not an app's support files: it is 153 G of evidence, experiment output and live source, written by the harness scripts under `scripts/`, which were never made safe for a path with a space (an upper bound of 50 unquoted lines in 18 files), and it includes Wine trees. It needs a durable folder with no space in its path; O3 says where.

Unchanged: the wrappers, one wrapper per game, both engines, the two log paths, CS2's deploy model (copies outside the repo, because an app may not run scripts from a clone under `~/Documents`: `scripts/setup.sh:14-15`), and Surviving Mars running from its checkout.

## 3. Design

**3.1 The folders are named once.** A new file, `common/paths.sh`, sets `L1_DATA_ROOT` and `L1_WORK_ROOT`, `CS2_DATA` (override: the existing `CS2_PATCH_DIR`) and `CS2_WORK` (override: `CS2_WORK_DIR`), by the rule in 3.3. From L1 step 1.6 on it also sets `SM_STATE` (`<data root>/surviving-mars-relaunched`) and `SM_WORK` (`<work root>/surviving-mars-relaunched`), each overridable by its own name and outside the old-install rule. Sourced, it sets them, under `set -eu` too. Run (`bash common/paths.sh`), it prints them as `KEY=value` lines, which is how a person, an agent or a Python script learns where things are; `scripts/check-experiments.py:37` reads the evidence store's place that way and stops if the call fails. Repo-side shell scripts source it by their own location (`"$(CDPATH= cd -- "$(dirname -- "$0")/../.." && pwd)/common/paths.sh"`) and take every default from `"$CS2_DATA"` or `"$CS2_WORK"`; each single-purpose override keeps its name and meaning, and only its default changes (`CS2_BUILD_DIR` stays one tree, default `$CS2_WORK/build-1116`). It exports nothing, so a child script sources it again; it warns on stderr if `CS2_WORK` contains a space. The only tracked code that spells either root is this file, its test, and the two `.command` wrappers (3.3). The roots are named after the repo, and the repo's name is a label: with the name written in four files and the app shim generated, renaming it is those edits, two `mv` and one `setup.sh` run (LT14).

**3.2 Deployed files find themselves.** They cannot source a repo file and do not need to: they are in the runtime folder.

| File | Change |
|---|---|
| `launchers/launch-cs2-dxmt11.sh:71` | `PATCH_DIR="${CS2_PATCH_DIR:-$(CDPATH= cd -- "$(dirname -- "$0")" && pwd)}"`; header lines `:9-10`, `:14` reworded without changing the line count, so the launcher lines this plan cites stay put |
| `launchers/launch-cs2.sh:102-103` | one `PATCH_DIR` line of the same form, used twice; comments at `:5` (the engine path; O4), `:12`, `:100` |
| the five PDX patchers' shared head | `_REVENV` is the first that exists of `revenv/bin/python3` beside the script's own `patches/` folder and, when `CS2_PATCH_DIR` is set, `$CS2_PATCH_DIR/revenv/bin/python3`; the error text names both. Edited identically in all five (LT5). Also the usage line `patches/patch_mkparent.py:30` |
| `repatch.sh:6`, `scripts/cs2-display-profile.sh:4`, `scripts/patch-modconflict-badge.py:41` | comments only |

This removes defect (1) of section 1. Two behaviours change, both for copies run straight from the checkout, which no caller in the repo does: a launcher started from `launchers/` prints its two "NOTE: no … in" lines (`:91`, `:188`), skips the badge step without a line (`:192-196`) and skips the patch check, where today it finds `~/cs2-patch`; and `bash repatch.sh` from the checkout stops at the first PDX patcher with "needs dnfile" unless `CS2_PATCH_DIR` is set, where today the patcher re-starts itself under `~/cs2-patch/revenv`. A launcher reached through a symlink looks beside the link. The documents say to run the deployed copies.

**3.3 An install made before this keeps working where it is, as one folder, until `setup.sh` moves it.** If `<data root>/cities-skylines-2` does not exist, and `~/cs2-patch` is a real folder (not a symlink), and neither root has been set to something other than its default, then `CS2_DATA` and `CS2_WORK` are both `~/cs2-patch`. Otherwise they are the two new folders. One observable decides both, so an old install is never half-moved by a default; and because a root counts as set only when it differs from its default, sourcing the file twice, or inheriting its values, changes nothing. `scripts/setup.sh` takes its folder from `common/paths.sh`, prints `data:` and `work:` lines under its `repo:` line, and for an existing install a line saying whether it will be moved (so `--check` shows all three), copies **both** launchers (the app still starts the `--stack` one), which removes defect (2), and warns when `~/cs2-patch` exists beside the new runtime folder. That state has more than one cause (a clone at an older commit ran `setup.sh` and recreated the old folder, or a folder was named by hand), so the warning says which folder the app's shim starts, and says to remove the old one only when the shim does not start it and it holds nothing but deployed copies; `scripts/check-experiments.py` reports the state as a problem until then. **`setup.sh` moves an existing install (O2).** When no folder was named (no `--dest`; `CS2_PATCH_DIR` unset, empty, or equal to the default runtime folder), `setup.sh` runs `scripts/move-install.sh` after its preflight has passed and before it copies anything. The move script, not `setup.sh`, decides whether there is anything to move, so the same call finishes a part-way move. Exit 0 (moved, finished, or nothing to move): `setup.sh` sources `common/paths.sh` again, takes its folder from it, prints the `data:` and `work:` lines again and goes on. Exit 1 (refused, nothing moved): it prints the reasons and goes on in `~/cs2-patch`, which keeps working, and its next run tries again; except that when the reason is a running game, Steam or launcher it stops there, because going on would copy over a launcher that is running. Any other exit: it stops before copying, with the move script's message, and exits 1. `--check` moves and creates nothing: it prints `move-install.sh --dry-run` in the header, under the `work:` line and before the preflight, and the header says "will be moved" or "cannot be moved now" as the dry-run says. After a move, `setup.sh`'s closing text says what went where, that anything of the owner's that names `~/cs2-patch` (a copied `.command`, an alias, a second app made with `make-shortcut.sh --name`) must be pointed at the runtime folder, and the line that declines. Declining is per run, `CS2_PATCH_DIR=~/cs2-patch bash scripts/setup.sh`; exported in the shell profile, it stands. `setup.sh` prints the line as that literal, `~` included (LT20a). If that variable names `~/cs2-patch`, the folder is absent and the runtime folder exists, `setup.sh` stops and says the install has already moved. The two `.command` wrappers carry the rule inline, because people copy them out of the repo (LT2).

**3.4 The move is a script, not typed commands.** `scripts/move-install.sh` does for anyone what L2 does on the Studio. It refuses, moving nothing, if `pgrep -x wineserver` finds a process or the launch lock of any wrapper under `~/Applications`, or of `$CS2_WRAPPER` (`<wrapper>/Contents/SharedSupport/prefix/.launcher.lock`), names a live one; if `lsof -a -d cwd` shows any of the user's processes with its working directory inside `~/cs2-patch` (the system does not refuse such a rename: the process is carried along under a path that no longer exists); if either target exists; if the old folder is a symlink; if the old folder and the nearest existing parent of each target are not on one volume; or if the checkout it runs from is inside the old folder. Then, if the old folder holds anything besides the runtime names, `.DS_Store` aside, it renames the whole folder to the workspace first and lifts the runtime names out of it into the runtime folder; if it holds nothing else, it renames the old folder itself to the runtime folder, one rename, and makes no workspace. In that order the rule of 3.3 never names a folder that is not there. A run that stops part-way prints the command that finishes it, and a second run finishes it: an absent old folder and a workspace that still holds runtime names is a state it recognises, and a finishing run leaves in the workspace, and names, any runtime name already present in the runtime folder. It exits 0 when it moved, finished an earlier move or found nothing to move; 1 when it refused and moved nothing; 2 when it stopped part-way. It takes its targets from `$L1_DATA_ROOT` and `$L1_WORK_ROOT`, never from `CS2_DATA`, which names the old folder until it has run. It changes nothing else. Run on its own, its last line says to run `setup.sh`; `setup.sh` runs it itself (3.3). `--dry-run` prints the refusals and the moves. Its test replaces the two process probes through one documented variable and takes the folders it expects from `bash common/paths.sh`, so it spells neither root. `INSTALL.md` gains a short paragraph: what `setup.sh` does to an install made before this, what stops working until it is copied again (a `.command` launcher copied out of the repo earlier still names the old folder), how to decline, which is per run, the three moves that put a folder back, and what to run after them (3.7): the line that declines, on every run, or `v0.1.0` for the old code as well. 128 people cloned this repo in the 14 days to 2026-11-08.

**3.5 Nothing is copied, snapshotted or rebuilt.** Every move is a rename on one volume, so each repo keeps its reflog, settings, shallow boundary and uncommitted files, and LT7 checks that. `CLAUDE.md` § Where things live records what the move does cost: each tree must be configured again before its next build, a rebuilt module is not byte-identical to the installed one because the build path is compiled in, and `revenv`'s console scripts and activation scripts hold the old path, so `revenv/bin/python3 -m pip` is the way to add a package. That the four trees are the only copy of their work is as true after the move as before it (section 7).

**3.6 Documents.** Comments, usage text and living documents name a place by its role ("the runtime folder", "the workspace", `<workspace>/evidence/…`) and give `bash common/paths.sh` as the way to print both, so they are true before and after a Mac's folders move. Living documents: both `CLAUDE.md` files, `INSTALL.md` (`:74`, `:200`, `:213`, `:222`, `:293`; the three commands a reader types against the runtime folder show the path quoted, and the uninstall line names both the old folder and the two new ones), `scripts/README.md`, `patches/README.md` (`:9,11` tell a reader to run `repatch.sh` from the checkout, `:41` says where `revenv` is made), `docs/agent-brief.md`, `docs/patch-inventory.md`, `docs/images/AUDIT.md`, `MODS-TESTING.md:194` and `PLAN.md`. Dated records keep the path they were written with: `EXPERIMENTS.md`, `GOTCHAS.md`, the 13 game plans under `docs/plans/`, `docs/dxmt-bugs/`, `docs/wine-bugs/`, `docs/perf-pass-results.md`, `docs/steam-ui-investigation.md`, `docs/test-matrix.md` (generated), the rest of `MODS-TESTING.md`, and the two root plans. The root `CHANGELOG.md` (3.7) is a record too, from the day each section is released: it names the old folder and both new ones outright, and LT12 allows it. The two mapping rules of section 2 go in one sentence at the top of `EXPERIMENTS.md` and of `GOTCHAS.md` and into `CLAUDE.md` § Where things live. Both `CLAUDE.md` files and the agent brief also say: never search or grant access above a `1launcher` folder, because `~/Library/Application Support` holds other apps' private data. The root `CLAUDE.md` names the old folder on five lines (`:16`, `:19`, `:23`, `:51`, `:65`): in L1 four are reworded by role, and its list of places allowed outside the repo (`:19`) names both roots for both games beside the old folder (the work root is on that list since Phase 3, for Surviving Mars's `engine/`); L2 drops the old folder from that line, when that becomes true on the Studio.

**3.7 Two releases bracket the move (section 0, D4).** A root `CHANGELOG.md` holds one section per release, `## v<number> (<date>)`, newest first, under a `## Unreleased` section for what `main` has and no release names yet. No other line in a section starts with `## `, and the date is the day the heading's commit was made, which can be a day before its tag. A release is an annotated tag and a GitHub release whose text is that tag's section, copied by a command and never typed into the page, so the words are reviewed in a commit and pass the checks every other document passes (LT13, LT20a):

```bash
sec() { git show "${2:-$1}:CHANGELOG.md" | awk -v v="$1" '{ sub(/\r$/, "") } index($0, "## " v " ") == 1 || $0 == "## " v { p = 1; next } /^## / { p = 0 } p'; }
sec v0.1.0 <commit> | grep -c '[^[:space:]]'     # 0 means a mistyped heading: stop
git tag -a v0.1.0 -m v0.1.0 <commit> && git push origin v0.1.0
sec v0.1.0 | gh release create v0.1.0 --verify-tag --title v0.1.0 --notes-file -
```

These are "the release commands". `sec <tag>` reads the tag's own copy of the file; `sec <name> <commit>` reads another commit's, which is how a section is read before its tag exists. Before them, in the checkout the tag is cut from: the commit is pushed and is on `origin/main`, and the unification plan's identity gate (its T5: the commit identity, the push credential and the `gh` login) names the project identity. A tagger and a release author are public and, by the rule below, permanent.

`v0.1.0` is the first release, and the last version whose `setup.sh` leaves an install in `~/cs2-patch`: it is cut in L1 step 1.0, before any code of this plan is pushed. `v0.2.0` is the move: it is cut at the end of L2, on the commit L2's tests ran on, so the release that moves people's folders has moved a real one first. Between the push of L1's code commit and that tag, `main` is ahead of the latest release, as it is in any project between releases, and the move sits under `## Unreleased`.

`v0.1.0`'s section says that it is the first tagged release; what the repo holds; that later commits on `main` make `setup.sh` move the install folder the next time it runs, and that `v0.2.0` will name that change; and that `git checkout v0.1.0` holds a clone here. Its page is the latest release for the whole time between the two, which is why it speaks of `main` and not of "the next release".

`v0.2.0`'s section says four things. What `setup.sh` now does to an existing install, and where the two folders are. What of the owner's stops working until it is pointed at the runtime folder (3.3's list). The line that declines, character for character as `setup.sh` prints it, as the way to keep the old folder and still get later fixes.
